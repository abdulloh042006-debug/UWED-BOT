# Architecture decision 001 — Telegram-only Worker pilot

The repository was empty; the local implementation starts from a small dependency-free Worker ESM application rather than introducing Django or a persistent polling process. The runtime boundary is `fetch(request, env, ctx)`. D1 is the structured store. Telegram updates use a secret-protected HTTPS webhook; outgoing messages are persisted in an outbox. R2 remains behind an evidence-storage boundary until its private access flow is implemented and tested.

The browser sends raw Telegram `initData` once to `/api/v1/auth/telegram`. The server verifies the HMAC and freshness, creates/loads the unique Telegram user and sets an HttpOnly, Secure, SameSite=Lax one-hour cookie scoped to `/api/v1`. All personal API routes check this session and object ownership. Frontend-rendered Telegram identity and route parameters are display hints only. Roles are stored server-side and changes audited. The first admin is granted only when the signed Telegram ID matches `BOOTSTRAP_ADMIN_TELEGRAM_ID` during first account creation. Provision and validate that secret before opening registration in a live pilot.

Domain operations are server-side. Request and session state transitions are validated in one place and DB uniqueness/transactions protect repeat actions. Store session timestamps in UTC and use a user timezone for display. Weekly availability overlap is scored only when both timezones match; this avoids false claims across DST zones. Private evidence uses a server-authorized R2 object key; files are never exposed by public object URL. This local code is not a production deployment until Sites bindings, migrations, secrets, webhook, real devices, backup and quotas are verified.

The Worker source has no provider-specific calls outside `env.DB`, optional `env.BUCKET`, `fetch` and Web Crypto. If Sites cannot host essential public webhook/private file behavior, the HTTP contracts can be retained while a separate backend is proposed for approval.
